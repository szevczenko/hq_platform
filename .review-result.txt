SEVERITY: HIGH
FILE: src/mongoose/mongoose_process.c
LINE: 120
ISSUE: MongooseProcess_Init() reads and resets the global lifecycle state without taking s_state_mutex, and creates s_state_mutex only after starting the poll task. A concurrent Init/Deinit can therefore initialize/reset mgr, queue, and control-connection globals while Deinit is freeing them; mutex creation failure is also ignored before osal_mutex_take() is called. This violates the required serialized initialization/shutdown boundary and can cause use-after-free or a crash.
SUGGESTION: Establish and validate the process-lifetime state mutex before any lifecycle work, and serialize the complete Init state transition with Deinit under it. Do not reset or replace manager/queue state outside that lock.

SEVERITY: HIGH
FILE: src/mongoose/mongoose_process.c
LINE: 195
ISSUE: Deinit ignores the stopped-semaphore timeout and unconditionally deletes the poll task, deletes the queue, and frees mgr. If the poll thread is still executing a callback or otherwise has not drained, queued/in-flight invocation records and Mongoose state are reclaimed while they may still be in use; a canceled in-flight record can also retain its poll-thread reference forever because its completion/release path is skipped.
SUGGESTION: Treat failure to observe poll-thread quiescence as a retained/retryable shutdown state. Do not delete the queue or free mgr until the poll task has drained/canceled every record and has been successfully joined; make the in-flight record cancellation path release its poll ownership exactly once.

SEVERITY: HIGH
FILE: src/wifi_provisioning/wifi_http_provisioning.c
LINE: 1072
ISSUE: When the HTTP close invocation fails, s_http_bound is cleared unconditionally even though http_listener_stop_cb() did not run and s_http_nc still owns the listener. A later stop sees the false snapshot and returns success without retrying the close, so STOPPED/ERROR no longer reflects the actual owned listener and a listener can leak or remain bound.
SUGGESTION: Clear the lifecycle snapshot only after a successful poll-thread close confirmation; retain the bound state and return ERROR on failure so a later serialized stop retries the same listener.

SEVERITY: HIGH
FILE: src/wifi_provisioning/wifi_provisioning_controller.c
LINE: 413
ISSUE: Controller mutex initialization is not serialized. init() calls _lock() before creating the mutex, checks/writes s_lock_ready without synchronization, and treats mutex-creation failure as a successful initialization while continuing with an effectively unlocked controller. Concurrent init/deinit/API or callback paths can consequently race controller state, contrary to TASK-138's mandatory cross-thread protection.
SUGGESTION: Create the process-lifetime mutex through a synchronized one-time path before accessing controller state, fail initialization if it cannot be created, and require all controller fields (including enabled and session) to be accessed under that valid mutex.

SEVERITY: MEDIUM
FILE: src/wifi_provisioning/wifi_provisioning_controller.c
LINE: 165
ISSUE: _start_grace() starts the timer and only afterward sets grace_timer_active. A timer callback or disconnect can run in that window and observe an inconsistent GRACE state; the callback can retire the session or the disconnect can clear GRACE, after which line 168 writes grace_timer_active true for an already-canceled/retired window. Timer start/change failures are also ignored while the timer is marked active, which can strand the controller in GRACE permanently.
SUGGESTION: Make timer arm/active publication a synchronized generation-aware operation, revalidate the session/state after each timer API call, and handle failed timer operations without leaving a false active GRACE window.
